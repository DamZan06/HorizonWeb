# 2. CRITICAL EXPEDITION STATE RULE

THIS RULE OVERRIDES THE CURRENT IMPLEMENTATION.

Current HORIZON logic incorrectly allows the planned start date to override Firebase data.

This is wrong.

The correct priority is:

```text
1. valid Firebase tracking data exists
      ↓
   EXPEDITION HAS STARTED

2. no Firebase data exists
      ↓
   use scheduled start date / pre-start state
```

Therefore:

**THE EXISTENCE OF AT LEAST ONE VALID TRACKING POINT MEANS HORIZON HAS STARTED.**

Do NOT return:

```text
not-started
```

if valid Firebase points already exist.

Refactor:

```js
getExpeditionState()
```

accordingly.

Suggested priority:

```text
finished override
        ↓
valid Firebase data
        ↓
recent point → live/moving/resting/etc.
stale point → delayed/offline/resting as appropriate
        ↓
NO Firebase points
        ↓
before planned date → not-started
after planned date → waiting-for-signal/offline
```

The scheduled date must NOT override real tracking evidence.


```text

```

localized with `Intl.DateTimeFormat`.
